# `urls` の定常歩行を連続最適化するために必要な情報

> この文書は設計検討時の論点を残した資料である。現在の確定仕様は `optimization_methods.md` と `implementation_conditions.md` を優先する。速度単位は m/s、目的関数の重みは $w_1=10,w_2=1$、速度の独立制約なし、遊脚は胴体弾道のみ、実装順は `elastic_approx` から、と決定済みである。

## 目的

`urls` の運動モデルを使って、格子探索を行わずに定常歩行の条件または入力を連続最適化するための設計事項を整理する。ここでは既存コードから確認できた内容と、新たに定義・確定が必要な内容を分ける。

## 結論

連続最適化は導入できる。`usls_forward` と同様に、最適化変数から運動を生成し、1回の数値シミュレーションからスカラー目的関数と制約を返す評価器を作る。ただし `urls` の現状は格子走査と合否判定であり、周期歩行の最適化器ではない。特に周期境界条件、最適化変数、CoTの定義、DAE失敗時の返し方を先に定義する必要がある。

格子探索を本番探索に使う必要はない。既存の走査結果は、初期値の参考や検証用ベンチマークに限って使える。良い初期値が既にあればそれを直接使い、なければ境界内の複数初期値から連続最適化を起動する。

## 既存資産から確認できた事項

### `usls_forward` の最適化パターン

- `ms_opt_main.m` は `fmincon` の interior-point 法を MultiStart から実行する。
- 第1段階は上下限付きの広い探索、第2段階は最良解近傍で許容誤差を厳しくした再探索。
- `ms_opt_fun.m` は変数から股・膝トルクのスプラインを生成し、Simulinkを実行して目的関数を返す。
- `opt_fun_forward_jump.m` は終端位置・角度・速度等の重み付き誤差を評価する。`urls` のCoT最小化とは目的が異なる。
- `usls_forward` の並列MultiStartは独立した初期点の評価に使われている。

### `urls` の現状

- `main.m` は4変数 `[Amp_h, theta_L, v, Duty]` を指定刻みで全列挙する。
- `solve_all_periods_dae.m` は立脚DAEと遊脚の胴体弾道運動を解く。
- `constraint.m` はトルク上限、トルク速度特性、移動距離、飛翔時間等を符号付き合否値として返す。
- 全条件合格した候補だけ `data_arrangement.m` に渡され、`v_ave_cot.m` で速度・CoT・距離を計算する。
- `main.m` 自体はCoT最小化を行わない。候補のフィルタリングと記録が主処理である。
- `parameter.m` の一般化座標は `[x,z,theta_h,theta_k,theta_a]`、股・膝トルクだけが入力で、足首角は4節リンク幾何で拘束される。
- `motion_equation.m` の運動エネルギーは胴体並進のみであり、脚リンク慣性や胴体回転を含む完全な剛体リンク力学ではない。
- `parameter.m` に上腿弾性トルク `tau_us` が定義されている一方、`motion_equation.m` の一般化力に明示加算されていない。上腿弾性の有効化をモデル仕様として確認する必要がある。

## 最初に決める最適化問題

### 1. 最適化の目的

次のどれを最適化するかを明示する。

1. 指定速度でCoT最小
2. CoTと速度追従誤差の重み付き和を最小
3. CoTを最小化しつつ、最低速度を不等式制約にする
4. 速度ごとのCoT最小解を得る速度スイープ（各点は連続最適化）

「定常歩行最適化」として解釈しやすい初期案は、**平均速度を目標値に一致させる等式制約、または許容範囲に入れる不等式制約の下でCoTを最小化**すること。目標速度自体も設計変数にするなら、速度に対するペナルティまたは速度範囲を必ず定める。速度制約なしでCoTだけを下げると、非現実的な低速・短距離解へ寄るおそれがある。

### 2. 最適化変数

既存の4変数を連続変数として使う案：

| 変数 | 現在の意味 | 決める必要があること |
|---|---|---|
| `Amp_h` | 水平方向床反力の正弦波振幅 | 単位、符号、上下限。床反力を制御入力として最適化してよいか、または関節トルクを直接設計するか |
| `theta_L` | 接地時の脚角（度） | 許容範囲と脚長・ストロークとの関係 |
| `v` | 目標平均速度（現在 km/h入力として m/s換算） | 固定目標か最適化変数か。単位をコード全体で統一 |
| `Duty` | 立脚期が周期に占める割合 | 下限・上限、および接地・離地イベントとの整合 |

現在の4変数を使うのが最小変更だが、`Amp_h` は関節トルクそのものではなく、モデルが仮定する床反力波形の振幅である。**床反力を最適化入力として扱うのか、股・膝トルク波形を最適化入力にするのか**を決定する。後者はより直接的だが、入力パラメータ化の追加が必要。

### 3. 周期・定常条件

周期性の状態ベクトルと接続条件を確定する。少なくとも、着地イベント直後と次の着地イベント直後の比較対象を定義する。

- 水平速度：次周期で同じ値
- 鉛直速度：接地・離地の衝突/リセット規約を考慮して周期接続
- 胴体高さ・姿勢：モデルに姿勢自由度がある場合は周期一致
- 股・膝・足首角と角速度：接触リセットを含む周期一致
- 水平位置：周期ごとの前進距離 `distance` だけ進む相対周期条件
- 立脚・遊脚の切替時に足先高さ、鉛直速度、接触力が物理的に整合

現在の `solve_all_periods_dae.m` は、初期状態を主に幾何と速度パラメータから構成して1回の立脚・遊脚を解く。一般化状態を周期固定点として反復収束させる処理や、周期残差を最適化制約として返す処理は確認できない。定常歩行を保証するには、次のいずれかが必要。

- 初期状態の必要成分も最適化変数に含め、1周期後との差を周期等式制約にする。
- 周期写像の固定点を内側反復で求め、収束した周期軌道のCoTを外側最適化へ返す。
- 周期残差をペナルティとして外側目的関数に加える（実用上はまず残差のスケーリングと収束確認が必要）。

どの方式でも、脚角の周期条件と、前進距離を伴う胴体位置の周期条件（相対周期条件）を分けて扱う。

## 目的関数とエネルギー評価に必要な仕様

現行 `v_ave_cot.m` は、立脚期の股・膝関節について

`E_act = integral_stance (abs(tau_h * dq_h) + abs(tau_k * dq_k)) dt`

を計算し、`CoT = E_act / (mass * g * distance)` とする。連続最適化の目的関数に採用する場合、以下を確認・決定する。

- 正味機械仕事ではなく正負仕事を別々に扱うか（現行式は絶対値で両方を正消費扱い）。
- 遊脚中のアクチュエータ仕事を含めるか（現行実装では遊脚トルクを0として連結している）。
- 弾性要素の蓄積・返還エネルギー、内部損失、モータ電気損失を含めるか。
- 距離がゼロまたは負の候補をどう制約・ペナルティ化するか。
- 実際の質量にEFLMリンク等を含めるか。`parameter.m` と `v_ave_cot.m` の質量内訳を一致させる。
- CoTを無次元指標として使うか、消費エネルギー/距離を直接使うか。

モデル比較が目的なら、`rigid`、`elastic_approx`、`elastic_exact` で目的関数と質量・モータ効率の扱いを同じにする。

## 制約として必要な情報

`constraint.m` の現在の±1判定を、そのまま最適化器の制約値に使うのではなく、余裕量を持つ連続値にする。各制約について単位、符号規約、正規化スケール、許容値を決める。

- 周期残差（状態ごとに代表スケールで正規化）
- 目標平均速度または速度範囲
- 股・膝の関節角範囲、足首リンクの幾何可動域
- モータのトルク速度包絡線を各時刻で超えない条件
- トルク上限、必要なら電流・電圧・熱制約
- 正の前進距離、許容ステップ周期、立脚時間・遊脚時間
- 足先の地面貫通なし、離地/着地条件、床反力の符号・摩擦円錐
- DAE解の成功、有限値、状態の許容範囲

最適化器が違反の大小を判別できるよう、例えば `c_i(x) <= 0` の形で違反量を滑らかに返す。初期実装では nonsmooth な `abs`、最大値、イベント切替を含む制約が有限差分勾配を不安定にし得るため、必要な平滑化や制約評価時刻の設計も記録する。

## 数値最適化器の選択と実装要件

### 推奨する初期構成

1. 1周期評価器 `evaluate_gait(x, model, options)` を作る。入力は設計変数、出力はCoT、周期残差、制約余裕、軌道、診断情報。
2. DAE初期化・状態スケーリング・失敗診断を評価器内で一貫して行う。
3. 既存4変数を用いるなら、まずは `fmincon` + interior-point でCoTを最小化し、周期残差と物理制約を非線形制約として返す。
4. 変数と周期残差の単位差を正規化する。有限差分幅、ODE/DAE許容誤差、制約許容誤差を別々に設定する。
5. 初期値は既知の実現可能歩容、過去ログ、またはユーザー指定値を使う。広域の格子を必須にしない。局所解対策として、少数の異なる初期値または解の近傍再最適化を選択可能にする。
6. 最適解について、周期残差・全制約・CoT成分・ソルバー終了理由を独立に再評価して保存する。

### 勾配と計算時間

- `fmincon` の有限差分は各変数の摂動ごとにDAEを解くため、1評価が高価だと勾配計算だけで多くの積分が必要になる。
- `urls` の `vpasolve`、記号式評価、DAE初期条件調整が評価時間の主要候補。最適化ループ内で毎回記号処理を行わず、数値関数を事前生成・キャッシュできる構造を調べる。
- 可能なら解析/自動微分可能な感度方程式、または適切な並列有限差分を検討する。ただしDAEイベントや分岐を含むため、勾配が安定しているか比較検証が必要。
- DAEの許容誤差を粗くしすぎると目的関数・制約ノイズが有限差分勾配を上回る。最適化許容誤差と積分許容誤差の整合が必要。
- 失敗候補へ固定の巨大値だけを返すと、近傍の改善方向が分からず探索が止まることがある。可能なら段階的な違反ペナルティまたは失敗原因ごとの制約を返す。

### 連続最適化だけで局所解を解消できるとは限らない

`MultiStart` は格子走査とは異なるが、複数初期点で局所最適化を繰り返すため、評価器が高価ならそれ自体も計算負荷になる。まず実現可能な1初期値で問題定義と周期条件を検証し、必要性が確認された範囲で初期値数を増やす。初期値生成には、Latin hypercube等の少数サンプル、過去解、解の近傍を利用できる。

## 現コードで特に先に確認する項目

1. `urls/main.m` が渡す `[Amp_h, theta_L, v, Duty]` と、`parameter.m` における速度換算・周期計算の単位を統一する（変数名 `v` は km/h相当の換算式だが、実行ログ・目的仕様では明記されていない）。
2. `constraint.m` の周期判定らしい `c1`〜`c3` が比較する終端状態と初期状態を追跡し、どの状態周期性を要求しているか検証する。現状は全状態の周期一致条件とは限らない。
3. `solve_all_periods_dae.m` の立脚終端・遊脚終端に接触切替イベントと状態リセットがどう反映されるかを確定する。
4. `v_ave_cot.m` の速度・CoTが目的とする物理量に一致するか確認する。周期歩行に合わせた分母距離と1周期時間の区間端点も検証する。
5. `tau_us` が運動方程式に加算されるか、弾性リンク質量・慣性をどのモデルで扱うかを決める。

## 推奨する作業順

1. 最適化タスクとCoTの定義を決める。
2. 周期固定点または相対周期制約を実装し、最適化を使わず既知歩容で残差を検証する。
3. 1周期評価器を作り、同じ入力で再現可能なCoT・制約・診断値を返すことを確認する。
4. まず低次元の既存変数で単一初期値から連続最適化する。
5. 感度・刻み幅・積分許容誤差を検証し、最適解を高精度で再シミュレーションする。
6. 必要になった場合だけ少数初期値のMultiStart/近傍再探索を加える。
7. 同じ目的・制約で各モデルを比較し、最適化成功率と計算時間も記録する。

## 参照ファイル

- `usls_forward/ms_opt_main.m` — MultiStartと2段階 `fmincon`。
- `usls_forward/ms_opt_fun.m` — 変数からトルク波形・Simulink評価への接続。
- `usls_forward/opt_fun_forward_jump.m` — ジャンプ終端評価。
- `urls/main.m` — 格子探索と合格候補記録。
- `urls/parameter.m` — 状態、幾何、力、弾性要素、歩行パラメータ。
- `urls/motion_equation.m` — 立脚・遊脚の方程式。
- `urls/solve_all_periods_dae.m`, `urls/solve_dae.m` — 1立脚・1遊脚のDAE解法。
- `urls/constraint.m` — 現在の成立条件・モータ制約判定。
- `urls/v_ave_cot.m` — 平均速度とCoT。
